## Goal

Deliver a desktop-optimized web app where a signed-in seller connects eBay, imports listings, receives grounded optimization suggestions, reviews every change, applies an explicitly confirmed batch, verifies the live result, and can safely undo it.

Success means:

- Two users cannot read or change one another’s listings, tokens, reviews, or batches.
- Closing the browser does not interrupt imports, analysis, apply, verification, or undo.
- The outgoing eBay write type cannot contain price, quantity, shipping, returns, images, condition, or other protected fields.
- Every successful write is read back and verified; interrupted jobs resume without blindly repeating writes.
- The documented lint, type, unit, database, browser, and production-build commands all pass.

## Architecture

```text
Browser
   │ authenticated HTTPS

Next.js web server ───────────────► PostgreSQL
   │                                     │
   │ enqueue job                         ▼
   └──────────────────────────────► durable queue
                                         │

                                    │     │      │

```

### Technical foundation

- **Web:** Next.js 16 App Router, React, TypeScript, Node 24 LTS, and pnpm. Pages use server rendering for initial data; mutations and progress polling use authenticated Route Handlers. Next.js documents Route Handlers as the App Router’s request-handler boundary ([Next.js](https://nextjs.org/docs/app/getting-started/route-handlers)).
- **Data and login:** Supabase PostgreSQL and Auth. Email login is invite-only for MVP. Every seller-owned table carries `user_id` and Row Level Security using `auth.uid()`; Supabase Auth is designed to integrate with PostgreSQL RLS ([Supabase Auth](https://supabase.com/docs/guides/auth), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)).
- **Secrets:** The eBay refresh token is stored through Supabase Vault; the eBay client secret, OpenAI API key, and other application credentials remain deployment secrets. Vault uses authenticated encryption and keeps backups encrypted ([Supabase Vault](https://supabase.com/docs/guides/database/vault)).
- **Jobs:** A separate Node worker consumes Supabase Queues/PGMQ. Queue messages contain only a job ID; durable state and progress live in ordinary tables. Supabase Queues provides PostgreSQL-backed durable delivery ([Supabase Queues](https://supabase.com/docs/guides/queues)). A worker is required because hosted function execution is time-limited and a large import or apply batch may exceed that limit ([Supabase function limits](https://supabase.com/docs/guides/functions/limits)).
- **AI:** An `AiAnalyzer` interface with an OpenAI adapter. The default is configurable `gpt-5.6-terra`, using the Responses API, `store: false`, and strict JSON-schema output. Official OpenAI documentation identifies Terra as the intelligence/cost-balanced model and confirms Structured Outputs support ([model](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Responses API](https://developers.openai.com/api/reference/java/resources/beta/subresources/responses)).

The strongest rejected alternative is running everything inside Next.js requests. It is smaller initially, but browser reloads, deployment restarts, and request-duration limits would make import and apply jobs unreliable.

## State ownership

- Supabase Auth owns application login and browser sessions.
- PostgreSQL owns all durable listing, analysis, review, batch, history, and progress state.
- The worker alone performs long-running external operations and batch state transitions.
- The browser owns only temporary filters, selected row IDs, expanded panels, and optimistic display state.
- eBay remains authoritative for live listing contents. AI output is an untrusted proposal until local validation and user confirmation.

## Database model

The first migration creates five groups of records:

1. **Identity:** `profiles`, `ebay_connections`, and one-time `ebay_oauth_states`. `ebay_connections` stores a Vault secret reference, never a plaintext refresh token.
2. **Listings:** `listing_snapshots`, `scan_results`, `traffic_cache`, `optimized_snapshots`, `aspect_dictionaries`, and `card_catalog_cache`.
3. **Analysis:** `analyses`, `suggestions`, `review_sessions`, and `review_session_listings`.
4. **Apply history:** `batches`, `batch_listings`, and `batch_changes`, including before, expected-after, actual-after, error, and verification state.
5. **Work:** `jobs`, with type, status, progress, cancellation, retry, lease, sanitized error code, and deduplication key.

Every user-owned record receives `user_id`, timestamps, foreign keys, and RLS. Shared Taxonomy and TCGdex caches are server-readable only. Migrations are append-only and tested with pgTAP.

## State ownership

### TanStack Query

Owns all server state:

- listings, filters sent to the API, and pagination results;
- connection status, analyses, review sessions, and suggestions;
- jobs, batches, history, and verification results;
- mutation state and cache invalidation.

WebSocket events contain only `jobId`, status, progress, and version. Receiving an event invalidates the generated TanStack Query key; it does not write authoritative workflow state directly into the browser cache.

### Zustand

Owns browser-only interaction state:

- selected listing IDs before analysis;
- open dialogs, expanded rows, and sidebar state;
- current client-side review focus;
- non-sensitive display preferences.

Zustand never stores listings, suggestions, review decisions, jobs, or batches. Review decisions persist through REST immediately.

### PostgreSQL

Owns every durable workflow and remains correct if the browser, API, WebSocket, or worker restarts.

## Authentication and user isolation

Better Auth uses invite-only email/password login for the MVP. Public registration is not exposed; the initial account is created with `pnpm user:create`.

Every seller-owned table contains `user_id`. User-facing database operations run through:

```ts
withUserDb(userId, transaction => ...)
```

That helper starts a transaction and sets a transaction-local PostgreSQL user ID. RLS policies compare each row against that value. API repositories accept only the scoped transaction type, making an unscoped query difficult to write accidentally.

The worker reads a job through its system connection, obtains its `user_id`, and performs all domain work through the same scoped database wrapper. Database tests prove two users cannot observe each other’s records.

Better Auth tables and application tables share Drizzle, but have one migration authority:

1. Better Auth generates its Drizzle schema.
2. Drizzle Kit generates reviewed SQL.
3. Only Drizzle migrations are applied.
4. `better-auth migrate` is never run independently.

## eBay credentials

The deployment owns:

- eBay App ID;
- eBay Cert ID;
- RuName;
- OpenAI API key;
- token-encryption key.

Users only see **Connect eBay Account**. Their eBay refresh token is encrypted with AES-256-GCM before storage. Each encrypted record contains ciphertext, IV, authentication tag, and key version so a later KMS-backed key rotation does not change the table shape.

The encryption service exposes only:

```ts
encryptRefreshToken()
decryptRefreshToken()
rotateRefreshTokenEncryption()
```

Plaintext tokens cannot be returned through REST, included in logs, or attached to Sentry events.

## REST and OpenAPI contract

Fastify routes use Zod schemas for params, query, body, success responses, and error responses. Every route also receives a stable `operationId`.

Generation flow:

1. `apps/api/src/openapi.ts` builds Fastify without listening.
2. `@fastify/swagger` emits OpenAPI 3.1.
3. Hey API generates the Fetch SDK and TanStack Query v5 options.
4. ESLint formats the result.
5. `pnpm api:check` regenerates into a temporary directory and fails on drift.

WebSocket messages use a separate discriminated Zod union:

```ts
job.subscribe
job.unsubscribe
job.updated
auth.expired
server.error
```

A subscription request authorizes every job ID before attaching the socket.

## Background jobs

`pg-boss` queues:

- `listing-import`
- `listing-sync`
- `listing-analyze`
- `batch-preflight`
- `batch-apply`
- `batch-verify`
- `batch-undo`

Queue payloads contain only the application `jobId`. User-visible progress lives in the application’s `jobs` table rather than exposing pg-boss internals.

Apply and undo use `group: { id: userId }` with concurrency one. Separate users may run concurrently, but one seller cannot apply and undo competing batches simultaneously.

After a worker transaction commits, it publishes a small PostgreSQL `NOTIFY`. Every Fastify instance receives the notification and forwards it to its connected user. A reconnecting browser fetches current state through REST, so missed notifications cause no data loss.

## Security model

### Authentication and tenant isolation

Better Auth provides invite-only email/password login. Public signup is disabled; `pnpm user:create` provisions users through the same Better Auth API used by the application.

Application queries run inside:

```text
withUserDb(userId, transaction)
```

That transaction calls `set_config('app.user_id', userId, true)`. PostgreSQL RLS policies compare each row’s `user_id` with the transaction-local value.

The API gets `userId` exclusively from the verified session. Workers receive only trusted `{ operationId, userId }` job payloads created by the API, set the same RLS context, and cannot access the auth schema.

### eBay token protection

- The deployment owns `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET`, and `EBAY_RUNAME`.
- Sellers see only Connect, Reconnect, Test Connection, and Disconnect controls.
- Tokens use AES-256-GCM envelope encryption with a key version.
- Development uses an explicit local key.
- Production uses a `TokenCipher` adapter backed by managed KMS.
- Access-token refresh locks the connection row to prevent concurrent refreshes.
- Tokens, descriptions, prompts, cookies, authorization headers, and XML bodies are redacted from logs and Sentry.

### eBay write boundary

`buildRevisePayload()` accepts only:

- title;
- full description;
- complete item-specific set.

No TypeScript input type or serializer field exists for price, quantity, shipping, returns, promotions, images, listing status, category, or condition.

Because eBay replaces the whole ItemSpecifics container, every update starts from a freshly fetched snapshot and merges approved changes into the unchanged remainder. [eBay documents the complete-replacement behavior](https://developer.ebay.com/DevZone/XML/docs/Reference/ebay/AddFixedPriceItem.html).

If legacy condition-like item specifics appear, item-specific changes for that listing are blocked and explained. Title or description changes may still proceed separately.

### Untrusted content

Listing titles, descriptions, and specifics are treated as untrusted data:

- XML parsing disables entities and DTD processing.
- Active HTML content is detected and removed only in the user-visible suggested description.
- OpenAI receives listing text as delimited data with no tools enabled.
- Model output passes Zod and domain validation.
- The apply allowlist remains authoritative even if a prompt-injected listing asks the model to change protected fields.

## Core domain behavior

### Sync and scanning

`canonicalizeListingSnapshot()` sorts item-specific names and values before hashing. `scanListing()` implements every Tier 1 rule in `SPEC.md` as pure functions with fixture tests.

Initial import:

1. Enumerate active listings with GetSellerList windows.
2. Fetch complete details and watch count with bounded concurrency.
3. Store immutable snapshots and update current pointers transactionally.
4. Run the local scan and emit progress after each listing.
5. Fetch daily traffic and monthly Taxonomy data separately.

Incremental sync walks `<48h` GetSellerEvents windows with two-minute overlap, deduplicates item IDs, and fetches flagged listings. A capped or unusable window triggers full re-enumeration.

### AI analysis

One listing is one Responses API request, with at most two concurrent requests per user. Completed listings are committed immediately, so cancellation keeps finished cache entries.

The prompt input contains the listing snapshot, Taxonomy dictionary, and resolved TCGdex facts. The output schema allows:

- at most one title suggestion;
- at most one description suggestion;
- item-specific set or remove suggestions;
- confidence percentage and one-sentence reason;
- evidence identifiers for factual card claims.

The server derives `HIGH`, `REVIEW`, or `UNCERTAIN`; the model cannot choose the behavioral tier directly.

`validateAnalysisOutput()` rejects protected fields, unsupported values, invalid lengths, false current values, ungrounded variant claims, and title suggestions for title-locked listings. Invalid schema responses retry once, then mark that listing as needing retry without inventing a result.

### Preflight and confirmation

Preflight fetches the current eBay state, compares its content hash with the analysis snapshot, validates the complete proposed result, and returns:

- eligible changes;
- excluded changes with reasons;
- literal listing and field counts;
- a server-generated confirmation hash.

Creating a batch requires the same hash and count. The server recalculates both; changing browser data cannot widen the write.

### Apply and crash recovery

Apply runs sequentially per seller under a PostgreSQL advisory lock.

Before each eBay call, the worker commits the batch listing, exact before/after plan, and attempt number. If the worker crashes after eBay succeeds but before the database update, resume first calls GetItem:

- already matches expected state → record success and verify;
- still matches before state → safely retry;
- matches neither → pause that listing as a conflict.

Auth errors pause the operation. Quota and transient errors reschedule with bounded exponential backoff. Permanent validation errors become per-field results and do not stop unrelated listings.

### Verification and undo

Each successful revise is followed by GetItem and one delayed read retry on mismatch. Only a verified listing receives a new optimized snapshot pointer.

Undo performs a fresh drift check against each batch’s after values. Safe listings default checked; drifted listings default unchecked.

Undo reconstructs complete item specifics from the latest snapshot, merges only the approved before-values, applies sequentially, and verifies. A batch becomes:

- `rolled_back` when every applied listing is restored;
- `partially_rolled_back` when only some are restored;
- unchanged when the user cancels before writing.

## Edge cases and dispositions

### Limits

| Case | Behavior and proof |
|---|---|
| 0 listings | Listings empty state; no Analyze action; Playwright fixture |
| 1 listing | Full workflow remains valid; end-to-end fixture |
| 499 / 500 / 501 selected | 500 accepted; 501 blocked by API and UI |
| Title 79 / 80 / 81 chars | 79–80 accepted; 81 blocked before approval |
| Aspect value 64 / 65 / 66 chars | 64–65 accepted unless Taxonomy lowers the limit; 66 blocked |
| 44 / 45 / 46 specifics | 44–45 accepted; 46 blocked |
| Description 499,999 / 500,000 / 500,001 chars | first two accepted; last blocked |
| No suggestions | Analysis completes, listing can be deselected, no empty review created |

### Failures

| Case | Behavior |
|---|---|
| eBay auth expires | Save progress, pause operation, show reconnect banner |
| eBay quota or transient failure | Reschedule with bounded backoff and visible delayed progress |
| eBay permanent rejection | Record exact field/message and offer valid exits |
| Taxonomy unavailable | Use unexpired cache; otherwise block item-specific suggestions |
| TCGdex cannot resolve card | Allow non-factual style suggestions only; no variant guess |
| OpenAI refuses or returns invalid output | Retry once, then mark listing retryable |
| PostgreSQL disconnects | Transaction rolls back; pg-boss retries from persisted state |
| SSE disconnects | Browser reconnects and refetches REST state |
| Sentry/telemetry fails | Application work continues; telemetry never blocks apply |

### Timing and concurrency

| Case | Behavior |
|---|---|
| Two browser tabs edit one review | Optimistic version conflict; stale tab refetches |
| Double-click Analyze/Apply/Undo | Same idempotency key returns the existing operation |
| Sync overlaps review | Existing review remains tied to its analysis snapshot; preflight catches drift |
| Listing changes during apply | Read-back exposes mismatch and pauses only that listing |
| Worker crashes after eBay success | Fresh GetItem proves whether to record or retry |
| OAuth callback is replayed | Single-use state rejects the second callback |
| Midnight, DST, timezone changes | UTC storage; browser-only human formatting |
| Two applies for one seller | Advisory lock permits one writer; second operation remains queued |

### Accepted service constraints

- One SSE stream per tab; deployment should use HTTP/2 and send heartbeats.
- PostgreSQL `NOTIFY` is non-durable and small, so it transports identifiers only.
- `pg-boss` retries still require idempotent handlers and read-before-retry logic.
- Better Auth and generated-client versions are pinned exactly and upgraded only through a green Renovate PR.
- Live eBay and OpenAI tests remain manual smoke gates; deterministic substitutes run in CI.
